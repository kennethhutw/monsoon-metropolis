# 20260806_CVA資格檢查與申請

## 變更摘要
新增 CVI/CVA 驗證專頁(Exporter/Importer 各一個),即時檢查錢包的 A-Token(CVA)收/轉資格(呼叫 `lib/cleanverse/apass.ts` 現有但沒人用的 `verifyApass()`),並加上申請流程 —— **申請不會自動核發,要經過 admin 審核通過後才會真的呼叫 Cleanverse 核發 CVI**。其他頁面(Repay、Apply)遇到資格不合格時,顯示提示 banner 導去驗證專頁,不重複整套 UI。Admin 新增一個審核清單頁面。

## 為什麼要 admin 審核(不是自助立即核發)
`/exporter/kyb` 現有程式碼裡,未驗證狀態的提示文字寫著:「An admin needs to issue one via KYB approval」—— 這是原本就設計好、但從沒真正接上的流程。這次補上,讓 demo 有「銀行/admin 審核後才核發合規憑證」的完整故事,呼應「compliant trade receivables financing」的定位。

## 變更內容

### 1. 資料庫:新增 `cvi_applications` 表(新 migration)
```sql
create table public.cvi_applications (
  id uuid primary key default gen_random_uuid(),
  wallet_address text not null,
  role user_role not null,           -- 目前只有 exporter/importer 會送出申請
  applicant_email text,               -- 從 session 帶入，非必填
  status text not null default 'pending',  -- pending | approved | rejected
  requested_at timestamptz not null default now(),
  reviewed_at timestamptz,
  reviewed_by text,                   -- admin email
  rejection_reason text,
  cv_record_id text,                  -- generate_apass 核發後填入
  chain_tx_hash text,                 -- registerCVI 上鏈後填入
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
create index cvi_applications_wallet_idx on public.cvi_applications (lower(wallet_address));
create index cvi_applications_status_idx on public.cvi_applications (status);
```
RLS 開啟、無 client 政策(比照 `case_news_scans`,全部走 service-role admin client)。

### 2. 新增共用 API:`app/api/contracts/cva-eligibility/[address]/route.ts`
- Real 模式:呼叫 `verifyApass('monad', contractAddresses.stablecoin, address)`,回傳 `{ eligible: boolean, code, message }`(`code === 4` 才算 eligible)
- Mock 模式:固定回傳 eligible,不打 Cleanverse

### 3. 新增 API:`app/api/cvi-applications/route.ts`
- `POST`:exporter/importer 提交申請,寫入 `status = 'pending'` 一筆(**不呼叫** `generate_apass`,單純建立審核請求)。同一個錢包已有 `pending` 申請時直接回傳該筆,不重複建立
- `GET ?wallet=`:查某個錢包目前的申請狀態(頁面用來顯示「審核中」「已核准」「已拒絕」)

### 4. 新增 API:`app/api/admin/cvi-applications/[id]/route.ts`
- `PATCH`:admin 審核動作
  - `{ action: 'approve' }` → 這時候才真正呼叫 `generateApass()` + `contracts.registerCVI()`,把 `cv_record_id`/`chain_tx_hash` 寫回申請紀錄,`status = 'approved'`,並寫入稽核日誌(CLAUDE.md 規則 7)
  - `{ action: 'reject', reason }` → `status = 'rejected'`,存 `rejection_reason`,寫稽核日誌

### 5. 新增頁面:`/exporter/kyb`(既有頁面,加強)
- CVI 面板旁邊加「A-Token Settlement Eligibility」卡片:呼叫 `cva-eligibility` 顯示即時資格
- 不合格時,依目前申請狀態顯示對應按鈕/文字:
  - 沒有申請紀錄 → 「Apply for CVI Verification」按鈕 → 呼叫 `cvi-applications` POST,建立 pending 申請
  - 有 pending 申請 → 顯示「Application under review」,不能重複送出
  - 被拒絕過 → 顯示拒絕原因 + 「Re-apply」按鈕
- 移除現有假的「Request Re-Verification」「Start Renewal」按鈕(只彈 toast,沒有實際呼叫),統一併入上面這個真流程

### 6. 新增頁面:`/importer/kyb`(新檔案,對稱 exporter 的頁面)
Importer 目前沒有身份驗證專頁(只有 Payables/Limits),這次仿照 `/exporter/kyb` 新增一個,結構相同(CVI 面板 + CVA 資格卡片 + 申請流程),差別只在 `role: 'importer'`。導覽列(`components/shared/Nav.tsx`)importer 選單加這個新頁面連結。

### 7. 提示 banner(不重複 UI,只導頁)
- `/exporter/apply`:提交申請前,如果偵測到目前連接錢包沒有已核准的 CVI/CVA 資格,顯示提示卡「Your wallet isn't CVI-verified yet — visit KYB Verification to apply」連到 `/exporter/kyb`
- `/importer/payables`:Repay 按鈕附近,同樣邏輯連到 `/importer/kyb`

### 8. 新增頁面:`/admin/cvi-applications`(審核清單)
- 列表顯示所有申請(錢包、角色、申請時間、狀態),預設篩選 `pending`
- 每筆 pending 的有 Approve / Reject 按鈕(Reject 需要填原因,比照 `bank/cases` 既有的 AlertDialog 確認模式)
- Approve 呼叫上面第 4 點的 API,成功後即時更新該筆狀態
- 導覽列 admin 選單加這個頁面連結

## 已知限制
- `verify_apass` 回傳的 `magickLink`(Cleanverse 自己的驗證連結)這次不用,核發一律走我們自己的 `generate_apass`,理由是穩定性優先(demo 前沒時間驗證 magic link 在 sandbox 是否每次可靠)
- Mock 模式下 CVA 資格檢查永遠回傳 eligible;要展示「不合格 → 申請 → 審核 → 核准」完整流程,必須在 real 模式下用一個故意沒註冊過 CVI 的新錢包測試
- 申請審核目前沒有通知機制(不會 email 或跳通知告訴申請人「已核准」),申請人要自己重新整理 `/exporter/kyb` 或 `/importer/kyb` 才會看到最新狀態

- 呼應 CVI/CVA 雙軌驗證的核心賣點,補上原本設計好但沒接的「admin 審核核發」流程,讓 CVA 也有即時 API 呼叫可以在 demo 影片裡展示

## 決策依據
Kenneth 確認要做獨立驗證頁面(而非嵌入既有頁面),並要求 admin 能看到申請清單。討論後發現 `/exporter/kyb` 現有提示文字本來就預期「admin 審核後核發」,這次補齊這個原本沒做完的流程,而非做成自助即時核發 —— 更符合「compliant」定位,也讓 admin 這條線多一個真的能操作的審核動作(不是唯讀,因為這不是案件核准/撥款這類已經鎖定給 bank 角色的動作,是全新的獨立審核流程)。
