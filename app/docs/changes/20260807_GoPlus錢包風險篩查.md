# 20260807_GoPlus錢包風險篩查

## 變更摘要
整合 GoPlus Security 的 Address Security API,對錢包做 phishing/sanctioned/money laundering 等風險旗標篩查。Exporter/Importer 在各自的驗證頁看到自己錢包的篩查結果;Bank 審核案件時**必須**篩查過雙方錢包才能 Approve —— 這是 AML(反洗錢)控制的一環,概念對應傳統金融的制裁名單比對。

## 為什麼分兩種失敗情境處理(避免明天錄影卡住)
GoPlus 官方文件列出的 `chain_id` 沒有 Monad,實際能不能查到 Monad 上的地址目前未知。如果做成「查不到也一律擋 Approve」,一旦 GoPlus 不支援 Monad,會讓 Approve 永遠卡住,毀掉整個 demo。所以拆成兩種情況:
- **API 呼叫失敗/查不到資料**(技術性問題)→ 顯示「Screening unavailable」,**不擋** Approve,提醒人工判斷
- **API 呼叫成功、真的命中風險旗標**→ **擋** Approve

「不檢查不能過」的精神仍然守住:一定要打過這支 API(不能跳過檢查這個動作本身),但技術性查不到不等於錢包有問題。

## 變更內容

### 1. 新增 `lib/goplus/client.ts`
- `getAccessToken()`:`POST https://api.gopluslabs.io/api/v1/token`,body `{ app_key, time, sign }`,`sign = sha1(app_key + time + app_secret)`,`time` 為目前 unix 秒數。Token 存記憶體快取,依 `expires_in` 提前一點過期就重新換發,避免每次查詢都重新認證
- `scanAddress(address, chainId)`:`GET https://api.gopluslabs.io/api/v1/address_security/{address}?chain_id={chainId}`,帶 `Authorization: Bearer {access_token}`。`chainId` 先試 Monad Testnet 的 `10143`
- 回傳型別涵蓋 GoPlus 文件列出的風險欄位:`phishing_activities`、`money_laundering`、`sanctioned`、`mixer`、`darkweb_transactions`、`stealing_attack`、`blacklist_doubt`、`blackmail_activities`、`cybercrime`、`fake_kyc`、`financial_crime`、`honeypot_related_address`、`malicious_mining_activities` 等

### 2. 新增 API:`app/api/contracts/wallet-security/[address]/route.ts`
- 呼叫 `scanAddress`,把上述欄位裡「值為 '1'」的旗標收集成 `flags: string[]`
- 回傳 `{ checked: true, flagged: boolean, flags: string[] }`(成功)或 `{ checked: false, error: string }`(GoPlus 呼叫失敗,包含 Monad 不支援的情況)—— **這支 route 本身永遠回 200**,失敗與否用 `checked` 欄位表達,不用 HTTP 狀態碼,避免前端誤判成一般錯誤

### 3. 新增共用元件:`components/shared/WalletSecurityCheck.tsx`
- Props:`address`、`label`(例如 "Exporter Wallet")、`onResult`(把結果回報給父層,用於 gate 邏輯)
- 掛載時自動呼叫上面的 API(不用手動按鈕,配合「一定要檢查過」的要求)
- 顯示三種狀態:
  - 檢查中 → Skeleton
  - Clean(`checked && !flagged`)→ 綠色「No risk flags found」
  - Flagged(`checked && flagged`)→ 紅色,列出命中的旗標
  - Unavailable(`!checked`)→ 橘色「Screening unavailable — manual review recommended」

### 4. `/exporter/kyb`、`/importer/kyb`
CVA 資格卡片下面加一個 `<WalletSecurityCheck address={address} label="Your Wallet" />`,純顯示,不影響這兩頁原本的申請流程。

### 5. `app/bank/cases/[id]/page.tsx`(`RealModeActions`)—— 這是這次唯一會影響既有行為的地方
- `PENDING_APPROVAL` 狀態時,Approve/Reject 按鈕上方加兩個 `WalletSecurityCheck`(exporter 錢包、buyer 錢包)
- 用 `onResult` 收集兩邊狀態,**Approve 按鈕的 disabled 邏輯**:
  ```
  disabled = 任一邊還在檢查中(loading)
           || 任一邊 checked && flagged（真的命中風險旗標)
  ```
  `checked === false`(技術性查不到)**不會**列入 disabled 條件
- Reject 按鈕不受此限制(隨時可以拒絕)

## 已知限制
- Monad 的 `chain_id` 支援與否要實測才知道 —— 如果一直是 unavailable,代表這次 GoPlus 整合在 demo 裡只能展示「有在打這支 API、有 UI」,無法展示「真的查到風險旗標」這個情境,除非用其他鏈的已知風險地址測試
- 沒有把篩查結果存進資料庫(不像 news scan 有歷史紀錄)—— 每次進案件頁都重新查一次,不做快取。之後如果要留審計證據(「核准時有篩查過」的紀錄),需要另開一次變更
- Bank 端這次改動會影響既有的 Approve 流程,錄影前務必先測過一次確認不會卡住

## 決策依據
Kenneth 確認錢包風險名單篩查是 AML 標準做法之一,要求 bank 審核時雙方錢包都要篩查過才能核准。考量到 GoPlus 官方文件未列出 Monad 鏈,又是明天(8/8 Hacking 期開始前)要錄 demo 影片的最後緩衝時間,選擇「檢查失敗不擋、真的命中才擋」的折衷設計,避免因為外部 API 對新鏈支援不確定而讓核心的 Approve 流程在錄影時卡死。
